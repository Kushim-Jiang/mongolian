## Hudum

**Comparison with [Quejingzhabu (2013)](https://search.worldcat.org/zh-cn/title/1133116484)**. Quejingzhabu (2013) introduces MONGOLIAN LETTER NA MEDIAL SEPARATE FORM for the letter <MNG links="n"/>. This presentation form is used as the initial <TOD links="N"/> in Todo <TOD links="n"/>, which is never used in Hudum. Therefore, this written form is not included in the Hudum part of this document.

More importantly, the naming principle for written forms used by Quejingzhabu (2013) differs significantly from this document, for example, naming the initial <MNG links="A" /> of the letter <MNG links="a" /> as the “third medial” form of the letter <MNG links="a" />. This is because it names the written form based on its position in the Mongolian word, where the front of chachlag and particles are not considered word boundaries. So the reason it says a written form is “medial” is because it is not preceded or followed by a word boundary. However, this document defines “medial” as joined both forward and backward.

**Comparison with [GB/T 25914—2010](https://openstd.samr.gov.cn/bzgk/gb/newGbInfo?hcno=62808E0BCB8246A287CFD9CF795ECF94)**. This document contains all the written forms of all the letters in GB/T 25914—2010 and can be regarded as an implementation of it.

**Comparison with [GB/T 25914—2023](https://openstd.samr.gov.cn/bzgk/gb/newGbInfo?hcno=BD6429DE5A7FC782FAAE13938A07166E)**. This document contains all the written forms of all the letters in GB/T 25914—2023 and can be regarded as an implementation of it.

**Comparison with [Liang (2019)](https://www.unicode.org/L2/L2019/19368-draft-utn-mongolian.pdf)**. This document uses the shaping process framework of Liang (2019) and presents the written units, phonetic letters, and logic of the shaping process in the same format. The main difference is that this document introduces positional default forms, fully uses dictionary-based particle shaping logic, and adds shaping rules as required by GB/T 25914—2023; whereas Liang (2019) uses fallback forms instead of default forms in the shaping process, minimizes the use of dictionary-based particle shaping logic, and does not include these additional shaping rules.

## Todo

**Comparison with [Quejingzhabu (2013)](https://search.worldcat.org/zh-cn/title/1133116484)**. Quejingzhabu (2013) introduces MONGOLIAN LETTER NA THIRD MEDIAL FORM for the letter <TOD links="n" />. This presentation form is used as the final <MNG links="N" /> in Hudum <MNG links="n" />, which is never used in Todo. Therefore, this written form is not included in the Todo part of this document.

Quejingzhabu (2013) introduces MONGOLIAN LETTER TODO LONG VOWEL SIGN FINAL FORM for the letter <TOD links="lvs" />. This presentation form consists of a chachlag and a long vowel sign, and is part of the ligatures like <TOD links="b a lvs" />, <TOD links="p a lvs" /> and so on. Since the behavior of the long vowel sign when added to a ligature is considered similar to a combining mark, the chachlag is not considered to be part of the long vowel sign, and thus this written form is not included.

**Comparison with [GB/T 36649—2018](https://openstd.samr.gov.cn/bzgk/gb/newGbInfo?hcno=289D5B6AB1E6B17173C5F5842D9B0C8D)**. This document contains all the written forms of all the letters in GB/T 36649—2018 and can be regarded as an implementation of it.

These presentation forms record different phonemes with MONGOLIAN LETTER ALI-GALI PA SECOND INITIAL FORM and MONGOLIAN LETTER ALI-GALI PA SECOND MEDIAL FORM, and thus are analyzed as the variant of <TODx links="p" /> in this document.

## Implementations

This document is the model; a font is one thing that renders it, and a normalizer is another. Both have to answer the same question—which written unit does this text produce—but they are asked it in different circumstances, and reading how each of them answers it is a way to test whether the model is stated clearly enough to be followed.

Where they meet is the shaping process. A font carries the process into the [glyph image layer](/introduction/#structure): it draws the written units and writes the substitution and positioning rules that the process prescribes. An engine that has no font to ask still has the same question to answer whenever it compares two texts, and the model answers it without a font, because the written unit a text produces is decided by the characters and the rules alone.

**[mongfontbuilder](https://pypi.org/project/mongfontbuilder/)**. The reference implementation that this repository maintains. It reads the rule data of this document, composes the [glyph image layer](/introduction/#structure) of a font from a minimal glyph set, and validates the result by shaping the test cases of the national standards with [HarfBuzz](https://harfbuzz.github.io/).

**[mongol-norm](https://pypi.org/project/mongol-norm/)**. A shape-aware normalizer, independent of this repository, by [Satsrag](https://pypi.org/user/satsrag/). It runs the shaping rules of this document without a font, so that two texts which look alike are found to be alike: it maps every encoding of a word—the same word typed with _a_ or _e_, with _o_ or _u_, with an FVS or a joiner—to one key, for search, deduplication, and indexing. Its engine is written in Rust and reaches Python as a thin binding, with a command line beside it.

The normalizer is not a font, and the difference is the point of comparing them. A font is asked for the written units of the text in front of it and stops there; the normalizer is asked whether two texts are the same, so it must also decide what to do with the freedoms that the model leaves to the text. Two things in it are worth a reader’s attention, because they are readings of this document rather than restatements of it.

_Reduction without a glyph set._ The lower layers of the process name glyphs—the basic mapping of phase Ia is a `cmap`, and the cursive joining of phase IIa assigns a joining position to the glyph of a letter. The normalizer has no glyph set, so it holds the written units a font would draw as names of its own, and the phases act on those names. This is what a font-independent implementation has to do, and the data of this document are what makes it possible.

_Normalization is not identity._ The output of its `normalize` is a key, not a recommended spelling. It encodes by glyph shape, so a word can come back written with different characters than it went in with—the normalizer’s own documentation gives <MNG links="m o ng g o l" /> becoming <MNG links="m o a g fvs2 n fvs1 n fvs1 o l" />—and it publishes a `canonical_version` for the key so that a caller can rebuild its index when the encoding changes. A reader who wants the standard spelling of a word should read the shape the normalizer reports, not the key it stores.

**Adding an implementation.** The list above is not closed. An implementation that follows this document is a reading of it, and a disagreement between the model and an implementation is usually a place where the model is not yet stated clearly enough to be followed—which is a report this document wants. If you have one, [open an issue](https://github.com/Kushim-Jiang/mongolian/issues) or send a revision to the UTN.
